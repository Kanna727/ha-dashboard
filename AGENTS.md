# AGENTS.md

Guide for AI agents (and humans) working on this repo. Read this before changing anything.

**Owner-specific facts** (the HA instance, household, device quirks, local paths) live in `CLAUDE.local.md`, which is gitignored. Read it if it exists. Never copy anything from it, or from `config/dashboard.config.ts`, into tracked files.

**Keep this file current.** Any PR that changes behaviour, architecture, the build/deploy workflow, or uncovers a gotcha updates AGENTS.md in the same PR. Facts about the owner's own setup go in `CLAUDE.local.md` instead.

## What this is

A custom Home Assistant dashboard written in React. It is **not** Lovelace. It builds to a single self-contained `index.html`, served from HA's `/config/www/dashboard/` (URL `/local/dashboard/index.html`). The per-home config is stored in HA behind its login (see Config below). It talks to HA over the WebSocket API using `home-assistant-js-websocket`.

The idea came from a Reddit post about a custom HTML dashboard with kiosk self-update, sun-following themes and a separate phone layout. The owner asked for React specifically, so unlike that post this project uses npm.

Targets:
- **iPad kiosk** (Kiosker app), `?layout=tablet`
- **ChromeOS wall tablet** (full-screen Chrome), `?layout=tablet`, with the screen-power extension in `kiosk-extension/`
- **Android phone**, `?layout=phone`
- **Desktop browser**, `?layout=desktop`

## Privacy rules (the repo may become public)

- **No personal data in tracked files**: no names, emails, account or device IDs, addresses, coordinates, IPs, local paths, or details about the owner's HA setup. That applies to code, comments, docs, fixtures, screenshots and commit messages.
- Every entity ID and name lives in `config/dashboard.config.ts` (gitignored). The committed `config/dashboard.config.example.ts` describes a fictional home, and `mock/fixtures.ts` matches the example.
- `scripts/privacy-check.sh` greps tracked files for private patterns (`.privacy-patterns` locally, the `PRIVACY_PATTERNS` secret in CI). Enable the hook once per clone: `git config core.hooksPath .githooks`.
- README screenshots come from the mock build only.

## Stack and constraints

- **Vite is pinned to 5.x**, so the project still builds on Node 18. CI uses Node 22.
- React 18, TypeScript (strict), `@mdi/js` icons, `vite-plugin-singlefile`, esbuild (evaluates the TS config at build time). `ws` is a dev dependency only so `scripts/push-config.mjs` runs on Node < 22 (no global `WebSocket`).
- No UI library and no CSS framework. Plain CSS with custom properties lives in `src/styles/app.css`.
- `.npmrc` in the repo pins the public npm registry on purpose. Don't delete it.

## Config (stored in HA)

- The release bundle is generic. All per-home data is in `config/dashboard.config.ts`, typed by `DashboardConfig` in `src/config/types.ts`. Keep it plain data: it travels as JSON.
- The `dashboard-config` Vite plugin evaluates it to `{ hash, config }` (hash = sha256 of the JSON, 8 chars). Dev and mock builds embed that via `virtual:dashboard-config` (mock always uses the example). Production builds embed `null` and write `dist/dashboard-config.json`. `DASHBOARD_CONFIG=<path>` overrides the source.
- In HA the `{ hash, config }` object is the whole config of a hidden storage-mode Lovelace dashboard, `dashboard-config` (not in the sidebar, `require_admin: false`). Unlike `/local/`, `lovelace/config` needs a logged-in user. `scripts/push-config.mjs` creates the dashboard if missing.
- The arranged card layout is kept the same way in a second hidden dashboard, `dashboard-layout` (`LAYOUT_DASHBOARD`), but written by the app itself, not by `deploy.py` (see Free canvas). Never push the config into it.
- The names the owner gives network clients live in a third one, `dashboard-names` (`NAMES_DASHBOARD`), also written by the app (see the Network popup). Never push the config into it either.
- Boot (`main.tsx`): use the embedded config, else the device cache (`localStorage.dashConfig`). With one, set `window.__DASHBOARD_CONFIG__` **synchronously, before any `await`**, then render. Without one (a device's first visit), connect (OAuth if needed), fetch with `lovelace/config`, cache it, and **reload**; the next load starts from the cache. If caching fails (storage blocked) it shows a message instead of looping.
- **Why the reload:** `vite-plugin-singlefile` inlines dynamic imports, so `import('./App')` is not lazy. Every app module runs as soon as `main.tsx` yields (its first `await`), whether or not the config has arrived. `entities.ts` therefore falls back to a complete `EMPTY` config so that module-level code (`TopBar`'s `LEAVE_ROOMS`, `MealsPanel`'s destructure) can't crash, and the app is never rendered with it. Don't add module-level code that assumes real config values, and don't move the window assignment after an `await`. The mock can't catch this (its config is embedded and set synchronously), so test the production boot as described under Verifying UI changes.
- When the helper's config half changes, `useSelfUpdate` fetches the new config into the cache before reloading.
- When adding a config key: update `types.ts`, both config files, the export list in `entities.ts`, and `mock/fixtures.ts` if it needs states. **New keys must be optional with defaults in `entities.ts`** (e.g. `ALERTS = { chime: true, doorOpenMinutes: 3, ...cfg.ALERTS }`): the config stored in HA can be older than the deployed app, and a required key it lacks would crash every screen. Push the real config to HA afterwards so its copy matches the file.

## Releases and deploys

- **Conventional Commits.** PRs are squash-merged and the PR title becomes the commit message, so the title must be `feat: …`, `fix: …`, `perf: …`, `docs: …`, `chore: …` and so on (CI checks it). `feat!:` or a `BREAKING CHANGE:` footer bumps the major version.
- On every merge to `main`, `release.yml` runs semantic-release. If there are `feat`/`fix`/`perf` commits since the last tag, it bumps the version, tags `vX.Y.Z`, commits `CHANGELOG.md` and `package.json` back (`chore(release)`, `[skip ci]`), and publishes a GitHub Release with `index.html` built from the example config. `docs`/`chore`-only merges make no release and deploy nothing.
- The deploy job joins the owner's tailnet (`tailscale/github-action`, OAuth client, `tag:ci`) and POSTs `{version, url}` to an HA webhook. `url` is a ~5-minute signed download link for the release asset (the repo is private). An HA automation checks the URL belongs to this repo, downloads it with the Downloader integration into `www/dashboard/`, and sets the helper. See `docs/home-assistant.md`.
- The release attaches `index.html` plus the app-install files from `public/` (`manifest.webmanifest`, `icon-192.png`, `icon-512.png`, `apple-touch-icon.png`), and the deploy job sends `{version, url, files: [{name, url}]}` with `index.html` last (`url` = index.html, for older automations). The automation only accepts those five names and this repo's asset URLs, downloads each in turn, and sets the helper only if every file arrived (a `failed` variable updated from inside the loop; else a persistent notification).
- In that automation the wait for `downloader_download_completed` runs **in parallel** with the download: `downloader.download_file` can block until the file is saved, so a wait started afterwards misses the event and times out.
- Running the Release workflow by hand (Actions → Release → Run workflow) redeploys the latest release when there is nothing new to release.
- **Helper format:** `input_text.dashboard_build` holds `"<app version>/<config hash>"`. The release automation replaces the first half; `deploy.py --config-only` replaces the second. Open pages reload when it differs from what they run. The `'dev'` version turns self-update off.
- The config is never deployed by CI (CI doesn't have it). Push it with `deploy.py --config-only` (needs `HA_URL` + an admin `HA_TOKEN`), or, as an agent with the HA MCP server, save `dist/dashboard-config.json` as the `dashboard-config` dashboard's config and update the helper's second half.
- Secrets/vars in GitHub: `TS_OAUTH_CLIENT_ID`, `TS_OAUTH_SECRET`, `HA_WEBHOOK_ID`, `HA_PREVIEW_WEBHOOK_ID`, `PRIVACY_PATTERNS`; variable `HA_TAILNET_HOST`. The deploy jobs skip with a warning if they are missing.
- **Preview deploys** (the owner asked for the local test version to be deployed with every change, at an endpoint apart from the live dashboard): the preview is the mock build (fake data from the example config, no HA connection) built with `VITE_PREVIEW=1`, which opens the sky test panel by default and shows the build version in it. `scripts/build-preview.sh <version>` writes `dist-preview/index.html` and `version.json`. HA installs it at `www/dashboard/preview/` (URL `/local/dashboard/preview/index.html`) through a separate automation, "Dashboard - install preview", on its own webhook (`HA_PREVIEW_WEBHOOK_ID`), so the live install automation and files are never touched; Downloader's `subdir: preview` does the placing. Setup: docs/home-assistant.md section 6.
  - **When:** every push to a same-repo pull request (`preview.yml`; forks and Dependabot get no secrets and must not run code on the HA origin), and every release (`release.yml`'s `deploy-preview`, which waits 60 s after the live deploy so the two automations' Downloader events don't interleave). The newest push wins; there is one preview.
  - **Only release assets:** like the live deploy, HA only accepts download URLs of this repo's release assets (any page on `/local/` runs next to the devices' HA tokens). Releases carry `preview-index.html` and `preview-version.json` (`.releaserc.json`); pull requests upload theirs to a rolling `preview` pre-release (never "latest"; its tag doesn't match semantic-release's `v*`). Versions are semver so HA's check passes: the release version, or `0.0.0-pr<N>.<sha7>`.
  - **Staying current:** HA serves `/local/` with a 31-day cache, so the page fetches `version.json` with `cache: 'no-store'` on load, every 5 minutes and when it becomes visible, and reloads with `?v=<version>` when it differs (one reload per version, so a stale file can't loop). `version.json` is installed after `index.html`. Mock builds skip `useSelfUpdate` (the mock helper says `dev`, which would otherwise look like a new deploy).


## Design

The visual design follows a reference screenshot the owner supplied: dark "panel" cards with uppercase letter-spaced labels, a greeting top bar with status pills and a big clock, tinted active states, and a chevron in each panel header that opens a detail modal.
- Panels (`.panel` + `PanelHead`) are the top-level cards. `.card` is the older, smaller card style, now only used inside modals.
- Detail views open through `useModal().open({ title, icon, accent, wide, subtitle, aside, body })`. The long-press sheet (`Sheet.tsx`: `LightSheet` for lights, the level sheet for fans) sits above modals (z-index 60 vs 45).
- **Card → detail zoom:** `ModalProvider` remembers the `.room-row`/`.panel` under the last `pointerdown`. When the View Transitions API exists (and reduced motion is off), opening gives that card `view-transition-name: modal-origin`, then inside `document.startViewTransition(() => flushSync(...))` moves the name to the `.modal` (class `morph`, which skips the `pop` animation), so the card morphs into the modal; closing does the reverse and clears the name when the transition finishes. Otherwise the modal pops in as before. Only one element may carry the name at a time.
- **Pages and the floating tab bar** (the owner asked on 2026-10-26 for separate pages with a floating tab bar like a dark pill-shaped one they showed): `PAGES` in `layout/pages.ts`, in this order:
  - **Fuller pages** (the owner asked on 2026-10-26 for every page to use the space, moving popup content onto the cards or replacing cards with their popups, and allowed resetting their arranged layouts): on tablet and desktop the main popups are on the page itself (`full` props); the phone keeps the cards and their popups. Each tablet column still scrolls on its own.
  - **Home is the glance page** (the owner asked on 2026-10-26: the wall tablet's default page, showing as much useful information as it can at a glance): `cols-home` (1fr 1.2fr): Rooms, and the "At a glance" panel (`panels/GlancePanel.tsx`). Phone: the glance panel above the rooms. Each tile (`components/GlanceTile.tsx`) opens its page. **Readable from across the room** (the owner reads the wall tablet from 5–6 ft on an 11" screen and asked for the tiles to work like the room chips, where the fills show fan speed, brightness and dishwasher progress): each tile leads with a 46 px number, a fill from the left (`level` 0–100 in `fill`), a ring, a strip or a big coloured icon, and an orange (`warn`) or red (`bad`) border; the 12.5 px label and 13 px `sub` line are for up close. Helpers: `GlanceBar` (a chip-like bar with a fill, lit while running), `GlanceRing`.
    - `WeatherTile`: temperature and a big weather icon, filled blue by the highest rain chance in the next 6 h (from 20 %), orange border for storms; → Commute.
    - `CommuteTile`: minutes, border orange for moderate and red for heavy traffic, the route as a thick strip coloured by live speed; the leave-later advice (or arrival) up close; → Commute.
    - `EnergyTile`: power now, filled against 4 kW, green, amber from 1.5 kW, red from 3 kW; the biggest plug up close; → Energy.
    - `CarTile`: fuel % as the fill (amber under 40, red under 20) and a big lock icon (green locked, orange unlocked or something open, grey offline); → Commute.
    - `NetworkTile`: download now, filled against the last speed test (how busy the line is); red "Down" when the internet is down; → Energy.
    - `BatteriesTile`: a big battery icon, green "OK" or orange with how many are low; → Energy.
    - `MealTile`: the next meal in 22 px type with the meal's icon, a dish per person or one "Both"; spans the row; → Health.
    - `CleanTile`: two `GlanceBar`s, the vacuum (battery as the fill, lit and saying what it does while it runs) and the dishwasher (progress as the fill, lit while it runs); opens Clean on whichever is busy.
    - `HealthTile`: per person a recovery ring coloured as WHOOP does (green, amber, red; the person's initial when there's no wearable) their weight in large type (from the scale only, never the wearable or riding account) and their FTP beside the name; two columns; → Health.
    - `MoneyTile` (`money/MoneyPanels.tsx`; spans the row, so the grid still comes out even): the days to the next card bill when one is due within a week ("2d", orange from 3 days, red when late) with the card and amount, else this month's spending; net worth (and the spending) beside it. Its amounts blur like the Money page's but a tap opens the page instead of showing them; → Money. Nothing without money helpers.
    - **Needs attention** (`panels/AttentionPanel.tsx`, helpers in `lib/attention.ts`, unit-tested; under the rooms on tablet and desktop, which go three across there; first on the phone): up to two items in 20 px type, worst first: `useIssues` (internet down, doors open, purifier faults, rain; not offline devices) in orange or blue, the dishwasher stuck (`actionrequired`/`error`), the car unlocked from 21:00 to 06:00, then green chores: the washer done within 4 h with its door not opened since (`washerDone`), the dishwasher finished. A card bill due within 3 days (or late) is an orange item that opens Money; it names the card but never the amount (anyone can read the wall screen). A tap opens the item's page; nothing → a green "All clear"; more than two → "+N more" in the header.
    - **Leave countdown:** with `COMMUTE.arriveBy` ("HH:MM", optional), inside the commute window the commute tile counts down to leaving (`leaveIn` in `commute/routes.ts`, unit-tested): "N min to leave", orange from 10, "Leave now", red "Late N min"; only from 2 h before until 1 h after.
    - **Air quality:** Google Air Quality (`google_air_quality`) is discovered from the registry (`findAirQuality` in `lib/airQuality.ts`, unit-tested; `components/useAirQuality.ts`): the Universal AQI (100 best; green ≥ 60, amber ≥ 40, red), its category and dominant pollutant as a line on the weather card and a bar on the weather tile. Without the integration nothing shows. Mock: `sensor.home_universal_air_quality_index` and friends.

Drags may not start within 20 px of a side (the system's back gesture). Swipes that start on something with its own sideways drag are ignored (`OWN_DRAGS`: the 3D car, sliders, the colour wheel, room chips, the music pill and player, `.chips-row`, arrange grips and handles, form fields, `[data-no-swipe]`). The vacuum page must stay swipeable to the other pages (the owner swiped back from it and nothing moved: the map and the 3D robot took half the page), so neither is on that list: the **map** sets `data-no-swipe` only while it needs the drag (zoomed in, following the robot, drawing, a shape selected or being dragged); at the fitted view a sideways drag on it turns the page, and when the pager takes a touch over it fires a bubbling `pagerdrag` event on the touched element, on which the map drops its gesture and undoes the few pixels it panned before the swipe was recognised. The **3D robot** turns with two fingers on touch screens (`controls.touches.ONE = null`, canvas `touch-action: pan-y`), so one finger swipes or scrolls the page; the mouse still drags it. Also ignored: swipes inside a sideways-scrolling element and swipes while a modal or sheet is open or cards are being arranged. Under reduced motion the page still follows the finger, but turns or springs back without the settling animation. Add `data-no-swipe` to any new element that needs horizontal drags.

## Loading, caching and connection status

- `src/ha/snapshot.ts` saves all entity states to `localStorage` (`dashSnapshot`, max age 24 h). It saves every 20 s when something changed, on `pagehide`/hidden, and right before a self-update reload. `HaProvider` hydrates the store from it before the first paint, so reloads draw the full dashboard immediately (about 80 ms) instead of a "Connecting…" screen. The spinner splash appears only on a device's very first load.
- The `HassApi` object in `HaProvider` is a **module-level constant**: its methods `await getConnection()`. Never put changing values on it. Connection status and user name come from `useHassStatus()` (`HassStatusContext`), with values `connecting` | `live` | `reconnecting`. An earlier version rebuilt the API object on every status change, which re-ran every `[hass]` effect (re-fetches, commute map rebuild) on each reconnect and caused flicker.
- The connection is a page-wide singleton that retries with backoff (2 s doubling up to 30 s). Only `ERR_INVALID_AUTH` clears tokens.
- `SyncIndicator` in the top bar shows "Syncing" or "Reconnecting" until live data arrives, then flashes "Synced" and hides.
- `useSelfUpdate` acts only when the status is `live`. The cached snapshot can hold an older helper value, and acting on it would loop reloads.
- The font uses `font-display: block`, which is fine because it's inlined.
- In the mock, `?mockSync=1500` simulates a slow connect and `?mockSync=reconnect` stays in the reconnecting state. `?mockFreeze=1` makes it deterministic for screenshot tests: no power jitter and no artificial delays; fake history is always seeded (mulberry32), aligned to 10-minute slots. `window.__mockPatch(entityId, { state })` changes a mock state from puppeteer. It exists only in mock builds.

## Night mode

`components/NightMode.tsx` (mounted in `App.tsx`) fades to a black night screen after `NIGHT_MODE.idleMinutes` (default 5) without pointer/key/wheel input, only on `NIGHT_MODE.layouts` (default tablet) and, with `nightOnly` (default true), only while `sun.sun` is below the horizon. It shows a big dim clock, date, temperature and condition, the `SkyArc`, and `useIssues()`. The block drifts a few px per minute (`driftAt` in `src/lib/night.ts`, unit-tested with `nightActive`) against burn-in. A touch wakes it; that pointerdown and the following click are swallowed so nothing underneath gets pressed. While it's up, `html.night` pauses every other animation and hides everything under it (`visibility: hidden`, the sky `display: none`), because CSS transitions (the moon glides on 60 s ones) and script animations don't pause, and ChromeOS takes a large area that keeps repainting for video and then never turns the display off; toasts (z-index 90) and full-screen alerts (95) still show and animate above it (z-index 80). `?nightTest=1` makes it kick in after 5 s at any time, for checking. Kiosker's own screensaver should be off so the two don't overlap. Underneath it, `IdleHome` has already gone back to the Home page (after 2 min), so a touch wakes to Home.

## Wall-screen power (ChromeOS)

The owner asked (2026-11-02) for the ChromeOS wall tablet's screen to really turn off at night and on vacation, and to wake when someone is in the living room or kitchen. A page can't switch a backlight off (the night screen only paints black), so a small MV3 extension in `kiosk-extension/` does it with `chrome.power`, loaded unpacked on the tablet (install steps in its README).
- `components/ScreenPower.tsx` (mounted in `App.tsx`, every layout) decides with `screenOn` in `src/lib/screenPower.ts` (unit-tested): on, except in `SCREEN_POWER.quiet` hours (default `['23:00', '06:00']`, may cross midnight) or while `VACATION_MODE` is on (`vacation`, default true), once the presence sensors of `SCREEN_POWER.rooms` (room ids; default every room) have all been off for `holdMinutes` (default 5). "Seen" uses the sensors' `last_changed`, so it survives reloads. `enabled: false` keeps it on.
- It posts `{ source: 'ha-dashboard', type: 'screen', on }` to its own window on every change and once a minute (the extension's service worker may restart and lose its state) and sets `html[data-screen]`. The content script (pages under `*://*/local/dashboard/*`, all frames) relays it to the worker, which calls `requestKeepAwake('display')` for on, plus `reportActivity()` (Chrome 113+, ChromeOS) when the last state wasn't on, to wake the display; `releaseKeepAwake()` for off. The display then goes off after ChromeOS's own idle delay, which can't be set on an unmanaged device. The worker answers `{ ready, canWake }`, which the page logs once.
- On the tablet, ChromeOS's power setting must be "While charging: Turn off display" (not Sleep, or the page stops and can't wake it) and "Show lock screen when waking from sleep" off. Without the extension (the iPad, phones, desktops) nobody listens and nothing happens.
- While the screen may go off, `NightMode` comes up after at most 1 idle minute at any time of day (`nightActive`'s `screenOff`, from the shared `useScreenOn()` hook), so the page under it stops repainting. Without that, ChromeOS's video detection (a region of about 333×250 px or more redrawing at 15+ fps) keeps the display on: the first version missed this and the tablet never went dark (2026-11-03). Once the extension has answered (`useScreenExtension()`), this holds on any layout: the owner's ChromeOS tablet got the desktop layout and had never shown the night screen. `NIGHT_MODE.enabled` must stay on for screen power to work. On the wall screen, the screen going back on (someone walked in, or the quiet hours ended) closes the night screen and counts as a touch, so the display wakes straight to the dashboard (the owner asked, 2026-11-03); at night it comes back after `NIGHT_MODE.idleMinutes` without a touch as usual. Other devices (the iPad) keep their night screen until touched.
- **Display entity** (the owner asked, 2026-11-11, for a switch in HA with history, to check the display really went off overnight): `SCREEN_POWER.entity`, an `input_boolean` the owner creates. Only the wall screen (the extension answered) touches it. It writes the screen's state into it on every change (so HA's history shows when the display was on or off), and reads a change made in HA as a command: a hand-set state (`Override` in `lib/screenPower.ts`, unit-tested with `effectiveOn` and `entityStep`) holds until the automatic decision next changes, so "off" by day lasts until 23:00 or until turned on, and "on" at night lasts until someone comes and goes or 06:00. Its own writes are told apart from commands by value and a 15 s window (`entityStep`); a stale entity on load or after HA restarts is just overwritten. Off by hand blanks the screen at once (`useScreenOffByHand()`), and a touch then cancels it. The override and the screen state live in a small store in `ScreenPower.tsx` that `NightMode` reads.
- What the entity records is what the wall screen did, not the backlight: Chrome isn't told when ChromeOS actually turns the display off (only a suspend hides the compositor), so "off" means blanked and released, with the backlight off after ChromeOS's idle delay if nothing keeps it awake. While the display may be off, the night screen is plain black (no clock).
- `?screenTest=1` treats every hour as quiet with a 15 s hold, for checking on the tablet. The mock can't switch a screen; check the messages with `__mockPatch` on a presence sensor and a `message` listener.

## Alerts (done, doors, and HA's phone notifications)

`components/Alerts.tsx` (mounted in `App.tsx` inside `ToastProvider`) watches live data only, never the cached snapshot: the washer `running` flag going on → off, the dishwasher going from running (progress 0–100 %) to not, any room or fridge door open longer than `ALERTS.doorOpenMinutes` (default 3, once per open episode), and **every notification HA's automations send to the phones**. Decisions are in `src/lib/alerts.ts` (unit-tested; the first reading after load never counts).
- **Mirrored HA notifications** (the owner asked for the phone notifications, laundry done, shoe rack opened and so on, to show on the wall dashboard too): `HassApi.subscribeNotifyCalls` subscribes to HA's `call_service` event and passes on every `notify.*` call, so any automation's notification shows with nothing to configure in HA. `ALERTS.notify` (default `['notify', 'mobile_app_*']`; trailing `*` is a prefix, `[]` turns it off) picks the services; `notify.tv` and the like are left out unless added. `noticeFrom` turns the call's data into the alert: the title (or the message when there is none) big, the message under it, the first emoji lifted out and shown as the picture (no emoji → bell icon), amber for ⚠️/🚨-type emoji or words like "left open"/"unlocked"; an automation can set the tone outright with `data: { dashboard: ok | warn | alarm }` in the notify call (wins over everything else; the companion apps ignore unknown keys), which is how the owner's alert automations pick green, warning or alarm; companion-app commands (`clear_notification`, `request_location_update`, the iOS kiosk mode's `kiosk_*`, ...) are skipped. One automation often sends the same text to each phone, so the same title+text within 10 s shows once.
- **Alarms** (the owner asked for the shoe-rack-opened notification to be an alarm): a mirrored notification is an alarm when its title or message contains one of `ALERTS.alarms` (any case; default none, the owner's config has the shoe rack), or when the automation sent it to the phones as one (Android `data: { channel: alarm_stream }`, iOS `push: { interruption-level: critical }` or `sound: { critical: 1 }`), so making an automation an alarm in HA makes it one here too. An alarm is red with the edges pulsing slowly (not a strobe, for photosensitivity), faster ripples, a shaking glyph (no emoji → `siren` icon) and an "Alarm" badge; it goes ahead of the queue, in front of an alert already showing; it has no lifetime bar and stays until tapped ("Tap anywhere to silence"); `siren()` in `lib/chime.ts` (three high-low square-wave beeps) repeats every 2 s for up to 2 minutes when `ALERTS.chime` is on, and then it stays up silently.
- **Dismissed when resolved** (the owner asked for a "door opened" alert to go as soon as the door closes): `Toast.dismissWhen` (`{ entities, states }`) takes a full-screen alert down the moment any of its entities reaches one of the states: the one showing leaves as if tapped (siren stops), a queued one is dropped unseen. `isResolved` in `lib/alerts.ts` (unit-tested) only counts a state reached after the alert came in, less 5 s of grace for a race, so an alert sent late (the away alarm goes out 2 minutes after the door opened) still shows when the door had shut before it arrived. Mirrored notifications set it with `data: { dashboard_dismiss: { entity_id, state } }` (each a string or a list, like a state condition); it only clears the dashboard, the phones keep theirs. Built in: a door-open alert goes when that door closes, "Washer is done" when the washer door opens. The store subscription runs only while some alert has a `dismissWhen`. Mock: the panel's "Door alarm (gone when it closes)" and "Door left open (closes in 6 s)" close the door themselves, since the overlay covers the panel.
- **Sound needs a touch after each page load** (chime and siren alike): browsers, iOS especially, block audio until the first tap, and a self-update reloads the page, so a kiosk that nobody has touched since a release shows alerts and alarms silently.
- **`call_service` is admin-only** in HA: a non-admin login gets `unauthorized` and nothing is mirrored (the subscription reports `ready(false)`). While mirroring works, the built-in washer/dishwasher "done" alerts stand down, because HA already announces those; with it off they come back. The door alert always runs.
- **Full-screen alerts** (the owner asked for them to be big and animated for the wall-mounted iPad): `Toast.full` in `components/Toasts.tsx`. One at a time over everything (z-index 95, above the night screen), queued ("1 of 3"), each up for `ALERTS.seconds` (default 30) from when it shows; a tap anywhere or Esc dismisses it and the next comes in. Tinted blurred veil with a slow conic sweep, a glowing orb with three ripples, the emoji or icon bobbing (shaking for warnings), title/text/"Home Assistant · 8:21 PM" rising in, and a bar along the bottom running down the lifetime. Reduced motion: no ripples, sweep or bob. The small corner toasts (15 s, top-right) are still used for action errors (layout not saved, vacuum command failed).
- `src/lib/chime.ts` plays a soft two-tone chime via Web Audio when `ALERTS.chime` (default true); the audio context is created/resumed on the first touch because iOS blocks audio until then, so the chime is silent before any interaction.
- **Mock:** the **Alerts test panel** (`mock/AlertsTestPanel.tsx`, a chip in preview builds, open at once with `?alertsTest`) fires sample notify calls (with a title; a shoe-rack alarm sent to two phones, matched by the example config's `alarms`; an alarm sent with `channel: alarm_stream`; a warning; three at once; a `notify.tv` one that must be ignored) and the dashboard's own washer and door alerts. `window.__mockNotify('notify', { message: 'Hi 👋' })` fires one from the console; a `notify.*` `callService` in the mock does too (`mock/notify.ts`). `?mockNotify=denied` behaves like a non-admin login (no mirroring, built-in washer alert back).

Both are off until turned on in the app, with notification access and an allow list of apps. Android only: iOS has no way to read another app's Live Activities.
- **What counts as live:** `android.requestPromotedOngoing` and `is_ongoing` both true. An app's ordinary notifications (offers) are ignored even when it is on the allow list.
- **What ends an island:** a newer ordinary notification from the same app, because a real order replaced its Live Update with one and `Last removed notification` never fired; that sensor also ends an island if it reports the Live Update itself; 90 minutes without an update (`LIVE_MAX_MS`), for a phone that went away. A reading with no words (a group summary, whose state is the package name) changes nothing, and a reading older than the island is ignored. An offer from the same app in the middle of tracking takes the island down until the app's next update.
- **The sensor holds one notification:** the list is built from its changes, and after a reload only what the sensor holds now comes back.
- **Privacy:** with no allow list the sensors carry every app's text (messages, one-time codes), so `ha/snapshot.ts` leaves them out of the snapshot it keeps in the browser, and only Live Updates are ever shown.
- **These aren't the Live Updates HA's own automations send to the phones.** Those are `notify.*` calls; the companion app leaves HA's notifications out of the sensor.
- **Mock:** the alerts test panel's "Live Update on a phone" group fills `sensor.phone_last_notification`: tracking starts, almost there, a second app, a third with no logo, delivered.

## Page sky

`components/SkyBackdrop.tsx` (mounted once in `App.tsx`) is a `position: fixed; z-index: -1` sky behind every layout, driven by `sun.sun`, the weather entity (state, `cloud_coverage`, `wind_speed` + unit, `wind_bearing`, `humidity`) and `HOME_ZONE`'s latitude/longitude. The owner asked for the whole dashboard's background to follow the weather and the time of day, then for the sun to rise on the right and set on the left, more frequent lightning, dense slow realistic clouds (moonlit at night), a tree and leaves for the wind, moisture, and the moon with its position and phase.
- **`#root { isolation: isolate }` keeps the sky visible.** Without it the sky's `z-index: -1` paints in the root stacking context, and anything that gives `<html>` a background (a dark-mode extension, a managed browser) stops the body's background from moving to the canvas, so the body's background covers the whole sky. That's how the owner saw a plain dark page in Edge on a work laptop. Keep everything inside `#root` (there are no portals), or the stacking breaks.
- **Scene** (`skyScene()` in `src/lib/skyScene.ts`, pure, unit-tested):
  - Sky colours: zenith/middle/horizon interpolated over sun-elevation stops (night −18°, blue hour −10°, civil twilight −4°, sunrise/sunset 0°, golden hour 5°, day 15°, high sun 45°), with a redder horizon in the evening (`rising` false). The weather greys, darkens or hazes them (`WEATHER` table) and sets the cloud cover (`cloud_coverage` refines it, in steps of 0.1, except for rain/fog/storm, which are always overcast).
  - Cloud colours come from the same stops (shaded base and lit top: white by day, gold at golden hour, orange/pink at sunset, moonlight at night), plus how strongly the tops are lit: by the sun by day, by the moon at night (its phase and height, never below 0.12 for skyglow), less under overcast.
  - **East is on the right.** `toScreen()` (`lib/astro.ts`) maps compass azimuth to x (`0.5 + 0.42 sin az`) and altitude to y, so the sun and moon rise on the right and set on the left. The sun uses `sun.sun`'s `azimuth`/`elevation`; without them, a plain-day model (`modelBody`: 06:00 east, noon south, 18:00 west) at the solar hour estimated from the rise/set times.
  - **Moon:** with a location, its real altitude/azimuth (`moonPosition`, the Astronomy Answers / SunCalc formulas, ~1°); without one (or in `?skyTest`), the plain-day model delayed by phase × 24 h. The disc (inline SVG: `moonLitPath`, maria, earthshine) is turned so its lit limb points at the sun's position on the page. It's faint by day, and hidden behind overcast like the sun's disc (`clearView`).
  - Wind: km/h (`windKmh` converts units), direction on the page from the bearing (blows towards bearing + 180°, east right; default leftwards), level 0–1 at 50 km/h. Moisture: `haze` only in rain, storms and fog (from humidity above 55 %, plus 0.25) and `dew` above 75 % (or rain).
- **Nothing between the pages and the sky** (the owner asked on 2026-10-26 for the page backgrounds to be fully transparent, with only the live sky and the city behind them): the flat `--bg` veil that used to dim the whole sky (and was mixed into the city colours) is gone, and the humidity haze only shows in rain, storms and fog (on a humid dry day it left a pale band that read as a grey film). The panels' own glass (`--panel-a`, more solid by day) keeps text readable, and the top bar's greeting and clock have a soft text shadow for bright clouds. The floating tab bar is translucent glass (38 % dark, blur 18 px, saturate 1.6).
- **Layers** (DOM order = paint order): gradient, horizon glow, stars, moon glow, moon, sun glow/disc/rays, clouds, city back (far and near skyline, windows, viaduct), metro trains, aviation lights, fog, haze, lightning glow/flash/bolt, city front (canopy, the tree's rise), rain/snow, tree, dew. So the sun and moon set behind the towers, low clouds sit behind them, and the bolt lands behind the canopy.
- **Clouds** (`cloudSvg` in `lib/skyArt.ts`): an SVG `feTurbulence` tile (stitched, so it repeats sideways), thresholded by cover into a density mask (`shape`; full cover closes every gap), and a `lit` mask from `feDiffuseLighting` on a height map, lit from the sun's/moon's direction on the page (30° steps). Each is a **CSS mask over a flat colour** (`--cloud-shade`, `--cloud-lit` at `--cloud-lit-a`), so colours change with the time of day without re-rendering the images; only cover or light-direction changes rebuild them, and the browser rasterises them once. Two layers (far 1100 px tiles, near 1600 px) slide by one tile width; ~4 px/s on a still day plus 0.3 px/s per km/h (5 km/h steps), with the wind's direction.
  - Height map = the cloud noise + a rounder billow noise (`0.0065`, 2 octaves), kept off its limits so nothing clips into flat plateaus, then blurred (8-bit heights otherwise light up as wood-grain contour lines). The noise is `feTile`d past both edges so the blur wraps instead of leaving a seam. Base frequencies are only mildly anisotropic; a big x/y ratio gave horizontal streaks.
  - **The masks are bitmaps** (`useBitmapMask`): each SVG is drawn once into a canvas and used as a PNG blob URL (cached, oldest freed). Used directly as an SVG mask, the browser re-ran the filters for every tile it rasterised, and a drifting layer keeps exposing tiles: frames stalled 0.2–0.9 s now and then in any cloudy sky. A layer appears once its bitmaps are ready, and keeps the old ones until new ones are (no blink when the light direction changes).
  - To inspect masks, draw each `mask-image` over a black div on white at its real height (puppeteer); headless screenshots of the sky alone hide most problems.
- **Thunderstorm** (`Lightning` in `SkyBackdrop.tsx`, `planStrike`/`boltPaths` in `lib/skyArt.ts`): one strike at a time on a JS timer, 0.7–5 s apart and biased short (bursts), at a random place across the page (6–94 %). Every strike lights the clouds around it (`.sky-glow`: an 80vw cloud texture lit from below, `cloudSvg(tile, 'lit', 90, 18)`, under a static radial light) and, more softly, the sky (`.sky-flash`, a 200vw radial). The owner asked for strikes all over the page, not one side, and for the clouds to glow.
  - **Keep strikes cheap** (the owner saw frame drops): the glow and flash stay mounted and are drawn once; a strike only sets their `transform` (to the strike's x) and flickers `opacity`, so nothing repaints. Things that caused drops and were removed: a glow inside the wide drifting cloud layers positioned by a CSS variable (repainted both layers per strike), `mix-blend-mode: plus-lighter` on it, a flash gradient positioned by a variable (full-screen repaint), CSS `drop-shadow` filters on the bolt (recomputed every frame of the flicker), and `getComputedStyle` per strike.
  - The glow rests at opacity 0.01, not 0 (browsers drop a fully transparent mask layer and couldn't rasterise it within a 0.3 s strike). WAAPI ignores the global reduced-motion CSS, so `Lightning` checks `prefers-reduced-motion` itself.

The panel shows a tree: Home total on the left, with a branch to each of the top 4 live consumers (≥ 5 W) stacked on the right. Each consumer row has its watts and a share-of-total bar. Each branch is a faint `.flow-track` plus `.flow-particles`: zero-length dashes with round caps flowing home → consumer. `src/lib/energyFlow.ts` (unit-tested) maps each plug's **own** watts (never its share of the biggest consumer: relative speeds made a 500 W and a 600 W plug look identical, and a lone plug always raced) to a level 0–8 on a log scale (each level doubles the watts from 10 W; speed 10 × 1.35^level px/s, ~10–110 px/s). Levels are whole steps with hysteresis (a reading must move 0.75 of a level past the current one; `EnergyPanel` keeps each plug's level in a ref), because changing `animation-duration` mid-run makes the dots jump. Density buckets come from the level too (light ≤ 4 < medium ≤ 6 < heavy, about 230 W and 900 W; gap 26/18/12 px, each with its own `@keyframes` shifting exactly one gap so the loop is seamless). Branches are short on the tablet (~40 px), so the speed spread is deliberately wide. Watt values render through the `Watts` component with `useTweenedNumber` (ease-out glide, rAF only while changing, skipped under reduced motion), kept as a leaf so per-frame re-renders stay small.

**Smart plugs are discovered automatically; there is no plug list to maintain.** A plug is a power sensor (`device_class: power`, `state_class: measurement`, W or kW) on a device that also has a `switch.*` entity. That takes in smart sockets and leaves out bulbs' power sensors (no switch), sensors without a state_class, and totals (no device). New plugs must show up with no setup, so keep both sides of the rule in sync:
- **HA:** `ENERGY.total` is a template helper that sums every reporting plug by looping over `states.sensor` with this rule; its availability template uses the same loop. (A `min_max` sum goes `unknown` as soon as one plug is unavailable, which blanked the circle, the peak and the chart.)
- **Dashboard:** `usePowerPlugs()` in `components/useHomePower.ts` applies the rule to the shared registry (`ha/registry.ts`, refreshed every 30 min, also used by the status dialog) and caches the list in `localStorage` (`dashPowerPlugs`) so reloads draw the rows at once. `ENERGY.plugs` only gives known plugs short names and fixed colours. A new plug is named from its HA friendly name minus " Power" (WiZ) or " Current consumption" (TP-Link), with an icon and colour guessed from that name (`PLUG_GUESSES`: speakers/woofers, vacuums and chargers too; a "speakers & charger" plug is a speaker), so renaming it in HA controls its label. A "TV unit" (the cabinet's router, streamer, set-top box, soundbar) gets `avUnit` in violet, so it never looks like the TV's own plug (`tv`, blue); keep that guess above the TV one. `useHomePower()` adds the offline list for the "X offline · total excludes them" note, and sums the plugs itself if the total sensor is missing. `fetchHomePowerHistory()` fills the start of the 24h window from `ENERGY.legacyTotal`. The Power popup lists every plug drawing ≥ 1 W.
- **30-day history** (Power popup, `EnergyHistory` in `components/EnergyCard.tsx`): `HassApi.fetchStatistics` → `recorder/statistics_during_period` (daily `mean`, long-term statistics, so beyond the recorder's ~10 days). `src/lib/energyHistory.ts` (unit-tested) turns mean W into kWh (× 24 h ÷ 1000; today × hours elapsed), splices `ENERGY.total` over `ENERGY.legacyTotal` per day, and averages complete days only. Bars grow in (transform `scaleY`, staggered); today's is hatched; tap a bar to read its day.
- Mock: the fixtures include an unlisted `sensor.bedroom_heater_power` plug and a bulb power sensor, to check discovery. `__mockPatch('sensor.bedroom_heater_power', { state: '900' })` puts the heater on the panel.

## Architecture rules

- **Every entity ID lives in the config** (`config/dashboard.config.ts`, mirrored by the example). Components read it through `src/config/entities.ts` and never hardcode IDs. (Exceptions: power plugs, car extras, batteries, the router, health devices, room bulbs and the doorbell are discovered at runtime, and `BUILD_HELPER` is fixed.) To add a device, add it to the right room's `controls` (a bulb only needs that for a custom label or `readOnly`). Anything that isn't a room control (energy, car, and so on) goes in its own section.
- **Room bulbs are discovered; a new one needs no setup.** `findRoomLights` (`lib/roomLights.ts`, unit-tested) takes every `light.*` in the room's HA area (the entity's area, else its device's; the area is `room.area ?? room.id`) that the room's `controls` don't list. Left out: entities with no device (HA light groups; `fetchRegistry` drops those), hidden lights (hide one in HA to keep it off the dashboard), `entity_category` ones, disabled devices, and lights with their own name (`en` in `entity_registry/list_for_display`): a bulb's light is the device itself and has none, while a fan's LED ring or a Zwift rider's power zone colour does. So a bulb whose *entity* was renamed in HA is skipped unless the name equals the device's: rename the device, or list it in `controls`. The label is the device's name minus the room or area and a trailing "Light" (`lightLabel`). `useRooms()` (`panels/useRooms.ts`) adds them after the room's listed lights, so read rooms through it (not `ROOMS`) whenever you need `controls`: `RoomsPanel` and the leaving-home button do; the list is cached in `localStorage` (`dashRoomLights`). A new bulb appears on the next registry refresh (30 min) or reload. Mock: `light.common_bathroom_common_area_light` is discovered, `light.bedroom_fan_led` must not be.
- **Read state with `useEntity` / `useEntities`**, never with a React context of all states. Power sensors tick every few seconds, and the per-entity store keeps re-renders local. `useEntities` returns a stable array reference when nothing has changed, so keep it that way.
- **Write through `useHass().callService`**. Both providers implement `HassApi`. If you add a new HA capability (a new WS command), add it to the interface in `api.ts` and implement it in **both** `HaProvider.tsx` and `mock/MockProvider.tsx`.
- `readOnly: true` on a control shows its state but blocks toggling. Don't remove it from a control without asking the owner.
- `confirmOff: true` on a control makes turning it off take two taps: the first turns the tile orange with "Turn off?", and a second tap within 4 s toggles it (`EntityTile`). Turning on stays one tap. Use it for things a stray tap shouldn't cut the power to, such as a PC on a smart plug.
- Lights and fans: tap toggles, long-press (450 ms) opens the lights sheet or the fan's level sheet. `useLongPress` cancels when the pointer moves, so scrolling on a phone never toggles anything. On the room cards, a horizontal slide on the lights chip sets the brightness and on the fan chip the quick fan's speed (both `useSlide`, which also does the chip's long press); keep the gestures' thresholds so taps, scrolls, slides and long presses never overlap.
- The mock provider must never end up in the production bundle. `main.tsx` only lazy-imports it when `import.meta.env.VITE_MOCK` is set. CI checks `grep -c MockProvider dist/index.html` is `0`, and that no entity IDs are in the bundle.

## Auth and security

- HA serves `/local/` **without authentication**. Never put tokens, API keys, secrets or personal data in the bundle.
- The live provider uses HA's OAuth flow (`getAuth`). Each device logs in once, and tokens are stored in that device's `localStorage` under `hassTokens`. `cleanAuthParams()` strips `auth_callback/code/state` after login.
- `deploy.py` reads `HA_TOKEN` from the environment only. It never writes the token to disk or into the build.
- Whoever can write `www/dashboard/index.html` can run code next to every device's HA tokens. That's why the deploy webhook only accepts download URLs of this repo's release assets, and its ID is a secret.
- Any public HA URL (Nabu Casa remote UI, Tailscale Funnel) exposes `/local/` to the internet, and such hostnames show up in certificate-transparency logs. That is why the per-home config lives behind the login and not in `/local/`.
- HA's HTTP server settings (port, reverse proxy, IP ban) are UI-managed since 2026.8 (Settings → System → Network → HTTP server), not `configuration.yaml`. Behind a reverse proxy such as Funnel, "Trust X-Forwarded-For" must be on with the proxy's address trusted; a request carrying `X-Forwarded-For` from any other address gets HTTP 400.

## Live preview with real data (`npm run dev:live`)

The owner asked to try changes against their own home without deploying (2026-10-26). `vite --mode live` serves the app at http://localhost:5173 (localhost only, fixed port) with the real config embedded, and proxies HA's `/auth`, `/api` (WebSocket too), `/frontend_latest`, `/frontend_es5`, `/static`, `/manifest.json` and `/local` to `HA_PROXY`. ## Gotchas

- **Car offline:** when the car's lock and fuel entities are both `unavailable` (the Kia Connect integration isn't returning data, typically an expired login; HA raises no repair or reauth flow for it), `CarPanel` treats the car as offline. It fetches the last numeric fuel/range/odometer/12V-battery readings from 14 days of history and shows them dimmed with "Offline · <age>", in the card and the detail modal. That query takes seconds on the Pi, so `loadLastKnown` keeps **one module-level result shared by the card and the modal** (in-flight request deduped, reused for 10 min, dropped when the car is back); a per-component fetch left the modal blank until it returned. Tyre warnings are back-filled too, via `fetchLastStates` (newest non-unavailable state per entity; `fetchHistory` keeps only numbers): dimmed, with a "Tyre pressure: last known, from <age>" note, and a last-known low tyre shows a "Low tyre (last known)" chip. Doors and lock are deliberately **not** back-filled: a stale "closed"/"locked" would mislead, so they stay unknown; the panel gets a "Kia Connect not responding" chip instead of the lock chip, and the detail modal a `.notice-banner` telling the owner to reconfigure the integration in HA. Lock is disabled and lock/door state reads "unknown"; never present an unavailable lock as "Unlocked". In the mock, `__mockPatch` the lock, fuel, range and odometer to `unavailable` to see it (mock history returns fixed car readings from 3 h ago, after a 1.5 s delay to mimic the Pi).
- **Registry reads can fail** (`loadRegistry`): a WebSocket drop while the device/entity registry is in flight rejects it (seen through the Funnel proxy in `dev:live`). ## Fan manual-override indicator

Fans can have an `input_boolean.*_fan_manual_off` flag (map: `FAN_MANUAL_OFF` in the config). While it's on, the fan's automations won't turn the fan on. `useHeldFans(room)` in `RoomsPanel.tsx` finds the held fans. The card itself isn't tinted (the owner removed the red edge and tint on 2026-10-21): a held quick fan's chip gets a red "Held" label and lock badge (other held fans get a "<fan> on manual override" line instead), and a banner in the room popup. Display only; the dashboard never changes the flag. The mock fixtures set the bedroom flag on.

## Automation thresholds (room readings)

The room cards colour a reading red when it is what keeps the room's fan or lights from switching on automatically, so the owner can see why an automation didn't fire. **Nothing is configured: the thresholds come from the automations themselves.**
- `HassApi.fetchAutomationConfigs()` lists `automation.*` from `config/entity_registry/list_for_display` and reads each with `automation/config` (failures skipped). `useGates()` (`ha/automations.ts`) fetches once per page, refreshes every 30 min and caches the parsed gates in `localStorage` (`dashGates`) so reloads colour at once.
- `automationGates()` (`lib/thresholds.ts`) finds `numeric_state` conditions (in `and`/`or`, `if`/`choose` branches, condition steps, and a lone `numeric_state` trigger; triggers are OR-ed, so not one among others) and pairs each with what its scope `*.turn_on`s: a condition in an `if` gates only its own `then`. Disabled conditions/actions, `attribute`/`value_template` and `not` are skipped. A limit can be an entity (input_number). State conditions OR-ed with a gate (e.g. a `*_temp_override` boolean) are bypasses: while one holds, the gate doesn't block.
- Room: the temperature gates whose targets are the room's fans, and the light-level gates whose targets are its lights. The light-level sensor isn't in the config: `ambienceSensor()` picks the one the room's "lights on below N" automations use most (so a room without such an automation shows none). Light level shows the sensor's unit when it has one.
- **Red** (`.room-row-readings .held`, `.stat-tile.held` in the room popup) when the automation is on, every one of the room's devices it targets is off (one light on already lifts the light level), and every such gate fails on the reading with no bypass on. Unavailable readings never go red. Off-automations ("fan off below 24") are ignored because they don't turn anything on. The popup tiles always show the rule ("Fan on above 27°"; "Fan needs above 27°" when held); the card readings have it as a tooltip.
- `RoomRow` evaluates against the whole store inside `useSyncExternalStore` but returns a JSON string, so cards only re-render when a rule changes.
- Mock: `AUTOMATIONS` in `mock/fixtures.ts`; the bedroom is too cool for its fan and too bright for its lights, so both read red. `__mockPatch('sensor.bedroom_bedroom_hub_temperature', { state: '27.5' })` clears the temperature.

## Top bar now-playing pill

`NowPlayingPill` in `TopBar.tsx` shows the first `MUSIC_PLAYERS` entity that is `playing`, else the first `paused` one (`activePlayers` in `MusicPlayer.tsx` lists playing then paused players; with several, swipe the pill or the popup sideways to cycle them, via `hooks/useSwipe.ts`, with dots as the indicator; paused shows a pause icon, "Paused ·" and dimmed art). ## Meals panel

`panels/MealsPanel.tsx` is a **menu board** (the owner picked it on 2026-10-21 from three candidate designs: "up next" hero, timeline, menu board): `MEALS.people` across (initial avatars, colours from `meals/parts.tsx`), `MEALS.slots` down. A dish everyone has spans the row with a "Both" tag (`shared`, case-insensitive). The next meal's row is highlighted and shows "by <end>" (`clock`) instead of its eating window (`time`); meals whose window has passed are ticked and faded (`slotStates`). Next meal = the first slot whose `end` (HH:MM) hasn't passed, else tomorrow's first slot, at which point the Today/Tomorrow toggle in the header defaults to Tomorrow; a manual tap holds only until that default flips (`useMealDay`). A day without a plan shows "No deliveries <day> · Eating out" and the next planned day's first meal (`nextPlanned`). `delivery` isn't shown.
- **Week popup** (chevron): one row per planned day (Monday first, Sunday last; `plannedDays`) with the meals as columns and today's row highlighted, a person filter (Everyone or one person) and the kitchen notes when `notes` isn't empty. At 600 px and below each day stacks its meals, every cell naming its meal, so phones don't scroll sideways.
- It sits on the Health page, next to the health card (see Pages). `fetchTodo` in the API is left unused.
- **Mock:** the **Meals test panel** (`mock/MealsTestPanel.tsx`, a "Meals test" chip in preview builds, open at once with `?mealsTest`) pins the meals clock (`setMealsClock` in `meals/useMeals.ts`; nothing else sets it) to breakfast, lunch, dinner or evening time and to any weekday (Sunday has no plan in the example), and "Same breakfast for everyone" copies the first person's breakfasts to everyone to show the merged row. Only the meals panel follows it.

## Building on Windows

A repo on Google Drive can't hold `node_modules` (`npm install` fails with EBADF). Set `BUILD_DIR` to a local folder and `deploy.py` mirrors the sources there, installs and builds. The default share target on Windows is `\\homeassistant.local\config\www\dashboard`. The `npm run mock` script uses POSIX env syntax; on Windows run `VITE_MOCK=1 npx vite build` from Git Bash in the build dir and serve with `python -m http.server`.
